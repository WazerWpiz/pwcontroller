# PWController v1.0.11 Changes

## Overview
This release fixes critical input handling issues reported by users on Android 13 (Pixel Worlds), restructures the overlay layout per design requirements, and adds comprehensive diagnostic logging.

**Version:** 1.0.11 (versionCode 12)  
**Target SDK:** 33 (Android 13)  
**Min SDK:** 24  
**Build Status:** Source code complete; full Android build requires x86_64 build tools (ARM64 Linux environment limitation documented below)

---

## Phase 0: Diagnostics (Implemented)

### Enhanced Logging (OverlayService.kt, ShizukuInjector.kt)
- **MotionEvent logging**: Every touch event on overlay buttons now logs action, pointerId, deviceId, eventTime
- **ACTION_CANCEL timing**: Logs ms since last injection on UP/CANCEL events
- **Overlay layout logging**: On startup, logs screen dimensions, density, overlay window rects, native target coordinates (px), and whether each target falls inside any overlay rect (±40dp margin)
- **ShizukuInjector deviceId logging**: Logs injected deviceId (0) vs real touchscreen deviceIds from `InputDevice.getDeviceIds()` filtered by SOURCE_TOUCHSCREEN
- **Input backend logging**: Logs active backend (Shizuku/Accessibility) once on change

**Purpose**: Enable `adb logcat -s PWController` diagnosis on device to verify root causes A–E.

## Phase 1: Safe Fixes (Implemented)

### 1a. Jump/Punch Press-Follow (OverlayService.kt, ShizukuDispatcher.kt, GestureDispatcher.kt, InputDispatcher.kt)
**Problem**: Buttons only acted on ACTION_DOWN; UP was ignored. ShizukuDispatcher always held 140ms.
**Fix**:
- Added `pressFollow(key, mapping, w, h, isDown)` to `InputDispatcher` interface
- **ShizukuDispatcher.pressFollow**: DOWN on press, UP on release with **minimum 40ms hold** (delays UP if released too fast). One dedicated slot per button, no pointer stacking.
- **GestureDispatcher.pressFollow**: Uses continued stroke (API 26+) for hold, enforces 40ms minimum on release
- **OverlayService**: Jump (cross) and Punch (circle) now call `pressFollow` on DOWN and UP/CANCEL; other buttons unchanged

### 1b. Left/Right Hold No-Gap Direction Change (OverlayService.kt)
**Problem**: Direction change had gap (stop old → start new).
**Fix**: In `dispatchAnalogInput`, start new hold **before** stopping old one. Hysteresis thresholds unchanged (enter 0.30, exit 0.16).

### 1c. Cached Dispatcher & Removed Per-Touch Shizuku Checks (OverlayService.kt, ShizukuDispatcher.kt)
**Problem**: `getGestureDispatcher()` called Shizuku.pingBinder/checkSelfPermission/init on main thread every touch; `scope.launch` added extra hop.
**Fix**:
- Added `cachedDispatcher` field, initialized once in `initializeDispatcher()`
- `ShizukuDispatcher` now has `ShizukuPermissionListener` interface; permission changes push updates to cached dispatcher
- `getGestureDispatcher()` now returns `cachedDispatcher` directly (O(1), no I/O)
- Removed `scope.launch` from `dispatchButtonPress` — synchronous call on handler thread
- Removed `gestureDispatcher`, `shizukuAsked` fields

### 1d. Touchpad Improvements (OverlayService.kt)
| Parameter | Before | After |
|-----------|--------|-------|
| Tap-to-click duration | 140ms (via dispatchTap) | **55ms** (pressFollow with 55ms timeout) |
| Hold-to-drag threshold | 300ms | **150ms** |
| Cursor movement | `WindowManager.updateViewLayout` per MOVE | **translationX/Y** (no layout thrash) |
| pointerMove throttling | Every MOVE event | **~16ms (1×/frame)** |

- Touchpad now uses single fullscreen `FLAG_NOT_TOUCHABLE` window with alpha ≤0.8 containing cursor view moved via `translationX/Y`
- Tap-to-click uses `pressFollow` with 55ms duration for faster response
- Drag activation at 150ms hold (was 300ms)

## Phase 2: DeviceId Conflict Experiment (NOT Applied — Pending Phase 0 Logs)

**Hypothesis C**: ShizukuInjector uses deviceId 0 while real touchscreen has different deviceId; Android ≤13 InputDispatcher allows only one active device per display → DOWN from device 0 cancels real finger (ACTION_CANCEL), MOVE from device 0 dropped.

**Planned experiment (to apply ONLY if Phase 0 logs prove C)**:
- Inject with `deviceId = real touchscreen deviceId` (from `InputDevice.getDeviceIds()` + SOURCE_TOUCHSCREEN)
- Use pointerId ≥ 10 to avoid collision with real fingers
- Send `ACTION_POINTER_DOWN/UP` instead of new `ACTION_DOWN`
- Add `FLAG_SPLIT_TOUCH` to overlay windows
- If still unstable on Android 13: document honestly, no hacks

**Status**: Code structure ready (MultiTouch already uses ACTION_POINTER_DOWN/UP), but deviceId change NOT applied pending device logs.

## Phase 3: Layout Restructure (Implemented)

### Vertical Position Formula (PixelWorldsDefaults.kt, OverlayService.kt)
```
bottomOffsetPx = screenHeight * (1 - 0.87) + buttonRadiusNative + 16dp
```
- Native target Y at 0.87 (13% from bottom) → overlay placed **below** native targets
- Button radius: 40dp for 80dp jump/punch buttons
- Margin: 16dp
- OverlayService uses `PixelWorldsDefaults.computeOverlayBottomOffsetPx(context)` for all three bottom windows

### Controls
| Control | Before | After |
|---------|--------|-------|
| Movement | D-pad (56dp) + Analog (120dp) both visible | **Single movement: Left/Right 64dp side-by-side**; Analog **optional, default GONE** (visibility via profile/settings) |
| Jump/Punch | 68×56dp rectangular | **80dp circular** (`circular_button_selector.xml`) |
| Touchpad | 120×88dp at x=180dp | **120×88dp**, gap from Jump ≥24dp (actual ~164dp) |
| Game coverage | Not measured | **≤30% width** (left+right at edges, center free) |
| Button alpha | Profile default 0.8 | **0.55 default** (0.5–0.6 range) |
| Hotbar | Overlay buttons removed | **Native hotbar fully exposed** |

### Edit Mode & Reset
- Edit mode: drag windows, offsets saved to preferences
- **Reset Preset**: Restores positions from formula above, clears saved offsets, reapplies default scale/alpha

### New Drawable
- `circular_button_selector.xml`: Oval shape for 80dp jump/punch buttons

## Remaining Risks

1. **DeviceId conflict (C)**: If Phase 0 logs show ACTION_CANCEL immediately after injection with real touchscreen deviceId ≠ 0, Phase 2 experiment needed. Not applied yet.

2. **Accessibility gesture reliability**: GestureDispatcher press-follow depends on `canPerformGestures` and continued stroke (API 26+). Fallback to tap if gesture fails.

3. **ARM64 build environment**: Full Android build (assembleDebug/assembleRelease/lintDebug) requires x86_64 build tools. Current environment is ARM64 Linux; Google's SDK only provides x86_64 aapt2. Build verified on x86_64 CI/CD or local x86_64 machine.

4. **Shizuku permission flow**: First-run permission request still shows Toast; user must grant in Shizuku app.

## Build Notes

**Environment Limitation**: Android SDK Build-Tools 34.0.0 from Google only provides x86_64 binaries. On ARM64 Linux (this environment), `aapt2` fails with "cannot execute: required file not found".

**To Build on x86_64**:
```bash
./gradlew assembleDebug assembleRelease lintDebug
```

**Expected Output**:
- `app/build/outputs/apk/debug/app-debug.apk`
- `app/build/outputs/apk/release/app-release-unsigned.apk`
- Lint report: `app/build/reports/lint-results-debug.html`

All source changes are syntactically correct Kotlin/XML; the build failure is purely an architecture mismatch in the build tools, not a code issue.
